# Солвер MESH

`Generate(cfg)` создаёт `lumo_solver.h` и `lumo_solver.c`
Поле `Files.Mesh` содержит невязку, термодинамику и численный якобиан
Размер системы фиксируется при генерации, состояние и режим передаются при запуске

```c
/* Storage owned by the caller; this example has static lifetime. */
static double workspace[LUMO_SOLVER_WORKSPACE_DOUBLES];
struct lumo_solver_report report;
int status = lumo_solver_solve(
    &operating, state, NULL,
    workspace, LUMO_SOLVER_WORKSPACE_DOUBLES, &report
);
```

До вызова `operating` подготавливается через [prepare](../prepare/README.md),
а `state` заполняется через [initialguess](../initialguess/README.md)
При сборке всех модулей общие файлы из `Files.Mesh` записываются один раз
с одинаковым описанием колонны для всех генераторов
Чтение JSON и сериализация результата остаются задачей будущего слоя запуска

## Алгоритм

Вычисляется невязка и якобиан, затем решается масштабированная система Ньютона

```text
r_scaled[i] = r[i] / residual_scale[i]
J_scaled[i,j] = J[i,j] * variable_scale[j] / residual_scale[i]
J_scaled * delta_scaled = -r_scaled
state_next[i] = state[i] + alpha * variable_scale[i] * delta_scaled[i]
```

Для плотной линейной системы используются исключение Гаусса и частичный выбор
главного элемента по столбцу с перестановкой строк
Порог малого элемента равен `64 * DBL_EPSILON` от наибольшего исходного элемента
масштабированной матрицы, поэтому статус вырожденности охватывает и некоторые
плохо обусловленные системы
Схема факторизации соответствует описанию [LAPACK DGESV](https://netlib.org/lapack/explore-html/d8/da6/group__gesv_ga831ce6a40e7fd16295752d18aed2d541.html)
Сама библиотека LAPACK не подключается

Метод Ньютона с поиском шага также описан в [PETSc SNESNEWTONLS](https://petsc.org/release/manualpages/SNES/SNESNEWTONLS/)
Здесь реализован простой вариант с уменьшением шага вдвое

```text
norm = max(abs(r_scaled))
norm_next <= (1 - 1e-4 * alpha) * norm
norm_next < norm
```

Составы и расходы проверяются перед оценкой пробной невязки
Допускается погрешность границ составов `1e-12` и расходов `1e-12 * sum(F)`
Выход за диапазон температур приводит к уменьшению шага
Компоненты состояния не обрезаются и не нормализуются
Сходимость означает достижение допуска по масштабированной невязке
Малость шага сама по себе не считается сходимостью

## Масштабирование и настройки

По умолчанию расходы масштабируются суммарным молярным питанием,
температуры начальными температурами ступеней, составы единицей
Характерный масштаб тепла равен максимуму начальных абсолютных QD и QW
и произведения суммарного питания на характерную начальную энтальпию фаз
Энтальпия для масштаба ограничена снизу единицей

Материальные балансы и замыкание делятся на масштаб расхода,
тепловые балансы на масштаб тепла, равновесие и суммы долей на единицу
Все масштабы фиксируются перед первой итерацией

```c
struct lumo_solver_options options;
lumo_solver_default_options(&options);
options.max_iterations = 100;
options.residual_tolerance = 1e-10;
int status = lumo_solver_solve(
    &operating, state, &options,
    workspace, LUMO_SOLVER_WORKSPACE_DOUBLES, &report
);
```

Можно передать собственные положительные конечные массивы масштабов
Вместо стандартного численного якобиана можно указать `options.jacobian`
и его `options.jacobian_context`, используя общий интерфейс MESH
Для стандартного численного якобиана автоматически задаются масштабы переменных

Начальные настройки дают 100 итераций, 30 уменьшений шага и допуск `1e-10`
`max_iterations = 0` проверяет только начальное состояние
`max_backtracks = 0` разрешает только полный шаг
Допустимый предел `max_backtracks` от 0 до 1000

## Результат и ошибки

Статусы различают сходимость, неверный вход, ошибку модели, вырожденный якобиан,
неудачный поиск шага, лимит итераций, численную ошибку и неверный рабочий буфер

`state` содержит последний принятый вектор и сохраняется при ошибке
до первого принятого шага
`report` содержит статус, число принятых шагов, число отклонённых проб,
итоговую норму невязки и норму последнего принятого шага
Если начальную норму определить не удалось, она равна `NAN`
`model_status` сохраняет статус ошибочного вычисления модели или якобиана
После принятого шага он сбрасывается в ноль

## Потоковая диагностика

Диагностику получает необязательный `observer` и его `observer_context`
Солвер передаёт запись синхронно, память контекста принадлежит вызывающему коду
Запись доступна только до возврата из callback
Солвер не сохраняет историю, для этого её копирует вызывающий код
Callback с типом `void` не прерывает расчёт и не должен изменять его входы,
состояние, настройки или рабочую память

```c
static void observe(const struct lumo_solver_iteration *record, void *context) {
    double *last_norm = context;
    *last_norm = record->residual_norm;
}

double last_norm = 0;
lumo_solver_default_options(&options);
options.observer = observe;
options.observer_context = &last_norm;
int status = lumo_solver_solve(
    &operating, state, &options,
    workspace, LUMO_SOLVER_WORKSPACE_DOUBLES, &report
);
```

При `observer = NULL` контекст игнорируется и дополнительные метрики не готовятся
Обязательный отчёт и вычисления, нужные алгоритму, сохраняются
Время callback входит во внешний замер расчёта

Событие `LUMO_SOLVER_INITIAL` передаётся после проверки входов,
первой невязки и масштабирования, его номер равен нулю
`LUMO_SOLVER_ITERATION` передаётся после каждого принятого шага
Номера принятых шагов начинаются с единицы
Для уже сошедшегося начального состояния передаётся одно начальное событие

Запись `lumo_solver_iteration` содержит следующие поля

- `residual_norm` норму масштабированной невязки
- `step_norm` норму фактически принятого изменения состояния в масштабе переменных
- `step_length` принятый множитель alpha, для начального события ноль
- `rejected_trials` число отклонённых проб перед этим шагом, для начального ноль
- `total_rejected_trials` суммарное число отклонённых проб
- `worst_residual_index` индекс строки MESH с максимальной по модулю масштабированной невязкой
- `worst_residual_value` её знаковое значение

При равенстве максимумов выбирается первая строка
Индексы строк нулевые, их смысл определён в [mesh](../mesh/README.md)
Норма последнего события совпадает с нормой в отчёте при успешном завершении

Отдельного события завершения или ошибки нет, итог сообщает `report`
Ошибка до первого корректного состояния не вызывает observer
При остановке после нескольких шагов уже переданные записи остаются у вызывающего кода
Отклонённые пробы не порождают событий
Поэтому при неудачном поиске шага финальное число отклонённых проб в отчёте
может быть больше числа в последнем событии
Контекст и накопленную историю сбрасывает сам вызывающий код

### Отключение при генерации

```go
files, err := solver.GenerateWithOptions(cfg, solver.GenerationOptions{
    Diagnostics: false,
})
```

`Generate(cfg)` по умолчанию включает поддержку observer
Флаг относится к генератору и не меняет физический JSON-контракт
При `Diagnostics: false` подготовка записей, вызовы и проверки observer
полностью исключаются из C-исходника
`LUMO_SOLVER_HAS_DIAGNOSTICS` в заголовке равен 0, в обычном варианте 1

Типы записей и поля настроек одинаковы для обоих вариантов
В сборке без диагностики `observer` и `observer_context` игнорируются
Вызывающий код может проверить макрос до подключения наблюдения
Сигнатура solve и рабочая память между этими вариантами не различаются

Старые поля `residual_history`, `history_capacity` и `history_count` удалены
Для накопления истории теперь используется callback с собственным контекстом
Решение и ограничения PoC описаны в [ADR-0006](../../doc/adr/0006-optional-diagnostics-callback.md)
API реализован, прежние цифры PoC не являются замером этой версии

Входы, настройки, массивы масштабов, память наблюдателя, состояние, отчёт и рабочий буфер
не должны перекрываться в памяти

## Рабочая память

Сгенерированные модули не вызывают функции динамического выделения памяти
Матрицу и рабочие векторы размещает вызывающий код в переданном массиве `double`
Размер равен `N*N + 7*N` элементов
`LUMO_SOLVER_WORKSPACE_DOUBLES` задаёт размер как константу для статического массива
Функция `lumo_solver_workspace_doubles()` возвращает то же число для внешнего API
Если размер в байтах не представим на целевой платформе, функция возвращает ноль
Размер передаётся в элементах, для числа байт его нужно умножить на `sizeof(double)`

Буфер должен иметь выравнивание для `double`, обычный массив его обеспечивает
Инициализация и очистка перед вызовом не нужны
После вызова содержимое рабочей памяти не определено и не является результатом
Один буфер можно переиспользовать при последовательных расчётах
Для одновременных расчётов нужны отдельные буферы и отдельные изменяемые данные
Показанный `static` массив подходит для последовательных вызовов
Обычный локальный массив тоже допустим, если позволяет размер стека

Нулевой указатель или недостаточная ёмкость дают `LUMO_SOLVER_INVALID_WORKSPACE`
Состояние и рабочая память при такой ошибке не изменяются
Изменена сигнатура `lumo_solver_solve`, старые вызовы нужно обновить

Память растёт как квадрат числа неизвестных, линейное решение как его куб
Это первая реализация для небольших колонн, универсальная сходимость не гарантируется

## Проверка

```bash
go test ./codegen/solver
```

Проверяется вся цепочка подготовки питания, начального приближения и солвера
На независимом эталонном случае сравнивается полный вектор решения
Дополнительно проверяются изменения режима, пять ступеней, три компонента,
несколько подач, различные масштабы, события наблюдения и остановки с диагностикой
Линейный решатель проверяется системой с известным ответом и перестановкой строк
Есть отдельный случай вырожденной MESH-системы с постоянными K = 1
Это проверка принятой идеальной модели, экспериментальная валидация не выполнялась

Отдельно проверяются размер рабочего буфера, отказ при недостаточной ёмкости,
сохранность границ массива и повторное использование без очистки
Регрессионная проверка запрещает вызовы аллокаторов во всех генерируемых модулях

В обоих вариантах генерации проверяются события, начальное состояние,
отклонённые пробы, ошибки и владение записями
Сборка без диагностики, observer = NULL и включённый observer дают побитово
одинаковое решение и одинаковые основные поля отчёта
