# Lumo

Lumo принимает описание идеализированной ректификационной колонны и генерирует специализированные исходники C99 для расчёта установившегося режима
Компилятор написан на Go, полученная модель решает систему MESH методом Ньютона

Минимальная задача состоит в расчёте разделения бинарной смеси, профилей по ступеням и тепловых нагрузок
Физические допущения и границы ответственности зафиксированы в [постановке задачи](doc/scope.md)

## Зачем

Проект исследует, как использование известной структуры колонны при генерации кода влияет на стоимость многократных расчётов
Размерность, компоненты, места подач и давление фиксируются в C-коде, питание и режим можно менять без перегенерации

Сейчас реализована базовая версия с численным якобианом и плотным линейным решением
Использование блочной структуры, другие производные и сравнение оптимизаций относятся к следующим этапам [исследования](doc/thesis_features_full.md)

## Как работает

```text
compiler_input.json → парсинг и валидация v1 → генерация .c/.h
                                                       ↓
                                            ручная компиляция C99
                                                       ↓
питание и режим → C API модели → профили, продукты и отчёт сходимости
```

Вход компилятора фиксирует структуру колонны и свойства компонентов
Контракт `model_input.json` описывает питание и режим, но CLI его не читает
Общая оболочка для чтения JSON и записи `model_output.json` ещё не реализована
Приложение вызывает C API и самостоятельно обрабатывает результат

[Архитектура](doc/architecture.md) связывает этапы, форматы и правила владения памятью
[Контракт v1](examples/v1/README.md) описывает JSON, [contracts/v1](contracts/v1/README.md) содержит Go-типы, парсеры и валидаторы

## Быстрый старт

Требуется Go версии из `go.mod`
Генерация исходников C99 без кода дополнительной диагностики

```bash
go run ./cmd/lumo -o generated examples/v1/benzene_toluene/compiler_input.inline.json
```

Для сборки с поддержкой диагностического колбека добавьте `-diagnostics`
Выходной каталог не должен существовать, его родительский каталог должен существовать
На выходе шесть модулей `.c` с заголовками, без `main`, динамической аллокации и операций ввода и вывода
Итоговый статус и отчёт расчёта доступны независимо от диагностики

Компиляция выполняется вручную, например GCC или Clang

```bash
cc -std=c99 -O3 -Wall -Wextra -pedantic -c generated/*.c
```

При линковке приложения подключаются все полученные объектные файлы и `-lm`
Порядок вызовов C API показан в [архитектуре](doc/architecture.md#вызов-модели) и [драйвере проверки](references/benzene_toluene_5x2/driver.c)
Пример `compiler_input.inline.json` содержит иллюстративные теплоёмкости и теплоты испарения
Ссылки `builtin` пока требуют внешнего разрешения в явные свойства `inline`

## Проверка и команды разработки

Для общих команд используется Make, список доступен через `make help`
Нужны Go, `gofmt`, C99-компилятор `cc`, Python 3 и Git

```bash
make build
make check
```

`make build` создаёт `bin/lumo`
`make check` проверяет форматирование, выполняет `go vet`, Go-тесты с компиляцией C99 и сквозную проверку 5×2
Отчёты сохраняются в `build/validation`, закоммиченные результаты остаются без изменений
Отдельные этапы доступны как `make fmt-check`, `make vet`, `make test` и `make validate`

`make fmt` форматирует Go-код, `make test-debug` сохраняет C-артефакты тестов для отладки
`make reference-check` пересчитывает и проверяет независимый эталон без перезаписи
Регенерация эталона остаётся отдельной явной командой из его документации

Инструменты можно переопределить через `GO`, `GOFMT` и `PYTHON`
`CC` выбирает исполняемый файл компилятора только для `make validate`, общие C-тесты по-прежнему вызывают системный `cc`
Переменные окружения Go, включая `GOCACHE`, передаются обычным способом
Прямые команды Go и Python также доступны, Make не обязателен для использования Lumo

[Независимый эталон 5×2](references/benzene_toluene_5x2/README.md) содержит входы, отдельный Python-расчёт, допуски и источники
[Отчёт](references/benzene_toluene_5x2/validation/report.md) фиксирует сравнение сгенерированного солвера с эталоном
Проверяется реализация идеальной модели, это не экспериментальная валидация свойств реальной смеси

## CI

[GitHub Actions](.github/workflows/ci.yml) запускает `make check` на push в `master`, pull request в `master` и вручную
Используется один runner Ubuntu с системным C-компилятором, Go из `go.mod` и Python 3.12
Кеш Go включён, новый запуск отменяет предыдущий для того же PR или ветки

Отчёт `validation-report` и оставленные при падении C-тестов каталоги `failed-c-tests` сохраняются на 7 дней
Если проверки остановились до валидации или C-тестов, соответствующий артефакт может отсутствовать
Номер файла и строки в диагностике относится к сгенерированному C или тестовой проверке

Путь от описания колонны до расчёта через C API работает и проверен на эталоне 5×2
Общие команды разработки доступны через Make, workflow CI настроен в GitHub Actions
Первый [удалённый прогон CI](https://github.com/ezyxip/lumo/actions/runs/40170483678) прошёл успешно
