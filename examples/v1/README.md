# Контракт v1: идеализированная колонна

Эта версия фиксирует новый формат задачи из [scope.md](../../doc/scope.md).
Схемы находятся в [schema/v1](../schema/v1/), соответствующие Go-типы —
в [contracts/v1](../../contracts/v1/types.go).

Для обоих входных файлов в `contracts/v1` реализованы строгие парсеры
и семантические валидаторы, пример вызова в [README](../../contracts/v1/README.md)
Проверка формата и параметров ещё не означает наличие готового расчёта
Подготовка состояния питания реализована в [codegen/prepare](../../codegen/prepare/README.md)
Решатель реализован в [codegen/solver](../../codegen/solver/README.md)
Разрешение ссылок на справочник пока не реализовано

Для входов с явными свойствами `inline` уже есть
[генератор термодинамики C99](../../codegen/thermo/README.md)
Он проверяет термодинамические параметры перед генерацией

Пример в [benzene_toluene](benzene_toluene/) показывает пару согласованных
входных файлов. Он не является исполняемым расчётом: ссылки `builtin`
с ревизией `example-v1` иллюстративные, такого справочника в проекте нет.
Для генерации доступен отдельный пример [compiler_input.inline.json](benzene_toluene/compiler_input.inline.json) на три ступени с явными свойствами
Он отличается от основного примера с `builtin` и содержит иллюстративные параметры энтальпии
Полный согласованный кейс на пять ступеней, независимый расчёт и результаты находятся в [эталоне 5×2](../../references/benzene_toluene_5x2/README.md)

## Два уровня

- `compiler_input.json` фиксирует компоненты и их свойства, число ступеней,
  конденсатор и кипятильник, давление, идентификаторы и места подач.
- `model_input.json` задаёт расходы, составы и состояния подач, расход
  дистиллята и молярное флегмовое число `R = L_1 / D`.
- `model_output.json` описывает продукты, профили и диагностику. Его схема
  уже задана, общая сериализация результата C API в этот JSON ещё не реализована
  Отчёт проверки 5×2 имеет собственный формат и не является `model_output.json`

Во всех документах обязательно `schema_version: 1`. Старые файлы без этого
поля относятся к прежнему контракту и не принимаются схемами v1.

Массив компонентов и составы по ID допускают больше двух компонентов,
массив и словарь подач — больше одной подачи. Минимальный проверяемый
сценарий остаётся бинарным с одной подачей. Возможность выразить другие
случаи в JSON не означает наличия проверенного расчёта этих случаев.

## Колонна и нумерация

Ступени нумеруются сверху вниз, начиная с 1. `column.stages` включает
полный конденсатор (ступень 1) и равновесный кипятильник (ступень N).
Подачи располагаются на ступенях от 2 до N−1. Несколько подач на одну
внутреннюю ступень допустимы, если имеют разные ID.

В v1 реализованы в формате только `condenser.type: total`,
`reboiler.type: equilibrium`, `pressure.type: constant`.
`equilibrium` описывает расчётное поведение кипятильника, а не его
конструкцию (kettle/thermosiphon). Будущие профили давления, частичный
конденсатор и боковые отборы потребуют явно описанных расширений схемы.

## Компоненты и свойства

`id` компонента — устойчивый ключ для составов; `name` — отображаемое имя.
Порядок компонентов в массиве не определяет смысл долей.
Молярная масса задана в г/моль.

`thermo.phase_equilibrium: antoine_raoult` выбирает закон Рауля с Antoine.
`thermo.enthalpy: ideal` означает идеальное смешение: молярные энтальпии
фаз складываются из чистокомпонентных с весами, равными мольным долям.

Свойства компонента задаются одним из двух взаимоисключающих вариантов:

- `source: builtin`, `key`, `revision`: точная ссылка на запись
  версионированного справочника. Запись должна содержать коэффициенты
  Antoine, модель энтальпии и диапазон температур. Неизвестные ключи и
  ревизии должны отклоняться до генерации кода; молярная масса должна
  совпадать с записью справочника. Сам справочник пока не реализован.
- `source: inline`: явные `antoine`, `enthalpy`, `temperature_range_K`.
  Коэффициенты Antoine используют строго
  `log10(Psat/mmHg) = A - B/(C + t_C)`; единицы обязательны.

Для inline пока определена простая модель `enthalpy.type: constant_cp`:

```text
h_liquid(T) = liquid_cp_J_mol_K * (T - reference_temperature_K)
h_vapor(T)  = vaporization_enthalpy_at_reference_J_mol
              + vapor_cp_J_mol_K * (T - reference_temperature_K)
```

Энтальпии — Дж/моль, температура — K. Ноль энтальпии жидкости задан при
опорной температуре каждого компонента. Теплота испарения — при этой же
температуре. Это явное приближение, а не универсальная корреляция свойств.
Параметры должны иметь источник; схема не подтверждает их физическую
достоверность. Общий диапазон `temperature_range_K` ограничивает применение
обеих корреляций компонента. Сложные корреляции можно добавить отдельными
вариантами `type`.

## Питание и режим

`composition.basis` — `mole` или `mass`; `fractions` содержит доли **всех**
компонентов, включая нулевые. `flow.unit` задаётся независимо от базиса
состава: `mol_s`, `kmol_h` или `kg_h`.

Состояние питания задаётся при давлении ступени подачи одним способом:

- `saturated_liquid`: насыщенная жидкость; температура определяется расчётом;
- `temperature`: задана `temperature_K`, фазовое состояние определяется
  равновесным расчётом при давлении ступени;
- `vapor_fraction`: задана мольная доля пара в общем расходе (0…1),
  температура и фазовые составы определяются равновесным расчётом.

Эти варианты не содержат независимого давления питания: рассчитывается
поток непосредственно на входе в ступень. Внешние клапаны и подогреватели
остаются за пределами модели колонны. Параметры прежнего формата `q`/`e`
не переносятся автоматически: новый `vapor_fraction` имеет явный молярный
базис и не является общей заменой параметра теплового состояния `q`.

`specifications.type: rating` требует расход дистиллята и молярное
флегмовое число. Чистоты продуктов — результаты расчёта. Design пока не
включён в схему.

## Семантические проверки сверх JSON Schema

Валидатор проверяет следующие условия

1. Уникальность ID компонентов и подач в compiler input.
2. Точное совпадение набора ID подач между двумя входными файлами.
3. Точное совпадение ключей каждого состава с набором ID компонентов,
   сумму долей, равную 1 с абсолютным допуском 1e-10.
4. Номера ступеней подачи в диапазоне [2, N−1].
5. Конечность чисел при построении структур из Go, а не только из JSON.
6. Для явных свойств min < max, попадание опорной температуры в диапазон
   и отсутствие полюса Antoine (C + t_C = 0) в допустимом диапазоне. Во время расчёта
   температуры должны оставаться в общем допустимом диапазоне свойств.
   Для `constant_cp` разность энтальпий пара и жидкости должна быть конечной
   и положительной на обоих концах диапазона, что покрывает весь интервал
7. Расход дистиллята меньше суммарного питания в том же базисе
   Для молярного расхода сравниваются моль/с, для массового кг/с
   Расходы питания пересчитываются с учётом их известных составов
   Состав дистиллята для этой проверки не требуется

Ссылки `builtin` проверяются только по структуре
Разрешение ключей и ревизий и сверка молярной массы со справочником
потребуют реализации самого справочника
До генерации кода ссылки нужно разрешить в `inline`
Массовая спецификация дистиллята в будущем потребует собственного
уравнения в решателе, её нельзя переводить в моль/с по составу питания

Схема проверяет структуру и локальные ограничения; она не может гарантировать
сходимость или физическую реализуемость выбранного режима.

## Результаты

Единицы выхода фиксированы: моль/с, K, Вт. Все составы — мольные доли по
ID компонентов. Так результаты не зависят от единиц входных данных.

`products.distillate` и `products.bottoms` — расходы и составы продуктов.
`condenser_duty_W` — положительная величина отвода тепла;
`reboiler_duty_W` — положительная величина подвода тепла.

`profiles` содержит ровно N записей по порядку ступеней. `liquid` — поток
жидкости вниз; у конденсатора это только флегма, у кипятильника — кубовый
продукт. `vapor` — пар вверх, у полного конденсатора он равен `null`:
формальные равновесные y из вектора Ньютона не выдаются за реальный поток.
Состав дистиллята совпадает с составом жидкости полного конденсатора.

При `diagnostics.converged: true` обязательны продукты, профили и
`mass_balance_error = abs(D + B - sum(F)) / sum(F)` в молярном базисе.
При несходимости результаты можно опустить; если они присутствуют,
это последнее приближение. `residual_norm` и `residual_history` относятся
к норме масштабированных невязок; точные масштабы и норму требуется
зафиксировать вместе с реализацией солвера.

## Совместимость

`topology/`, схемы непосредственно в `examples/schema/` и примеры 01–03
сохраняют прежнюю версию. Их CMO-результаты не являются эталонами полного
MESH-расчёта с тепловыми балансами. ADR-0001–0004 и старые документы описывают
историю проекта; для нового формата источником истины служат эта страница
и схемы v1. В частности, прежние плоские поля единиц, параметры q/e и
формат одиночных долей компонентов к v1 не применяются.

## Проверка контракта

```bash
go test ./...
go vet ./...
uv run --with jsonschema python examples/v1/validate_contracts.py
```

Go-тесты проверяют строгий парсинг, семантику обоих входов, связи между ними,
перевод расходов, сериализацию и представление нулевых/отсутствующих величин

Python-скрипт проверяет три схемы по Draft
2020-12, допустимые и недопустимые варианты данных и связи в паре примеров.
Пользовательские входы проверяются Go-парсерами и валидаторами
