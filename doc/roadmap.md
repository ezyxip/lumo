# Дорожная карта: Кодогенерация для MESH-моделей ректификационных колонн

## V0 — Работающий сквозной пайплайн

**Срок:** к концу месяца 3

**Описание.** Минимальный компилятор, доказывающий саму концепцию: описание топологии колонны → сгенерированный C99-код → решение MESH-уравнений. Никаких оптимизаций производительности — только корректность.

**Состав:**
- Формат описания топологии (JSON/YAML): ступени, их типы (feed / simple / condenser / reboiler / side-draw), состав фида, число компонентов
- Кодогенератор, транслирующий это описание в наивный C99-код (без развёртки циклов, без SIMD, без SoA)
- Решение методом Naphtali-Sandholm (полный одновременный Ньютон)
- Якобиан — finite differences
- Solver — dense LU
- Precision — f64 только
- Line search — включён с самого начала (как fixed baseline-компонент, не опция)
- Один тестовый кейс: 5 ступеней × 2 компонента (Antoine + ideal Raoult)

**Критерии выполненности:**
- [ ] Компилятор принимает описание топологии и генерирует компилируемый без ошибок C99-код
- [ ] Сгенерированная модель сходится на тестовом кейсе (Converged: yes)
- [ ] Результат (составы, температуры, потоки по ступеням) сверен с независимым эталоном (ручной расчёт или DWSIM) — отклонение задокументировано и находится в допустимых пределах
- [ ] Есть written-up описание архитектуры компилятора (для главы 2–3 диплома)
- [ ] Наличие этой версии не зависит от прогресса по V1+ — то есть работа защитима "как есть"

## V1 — Первый содержательный результат: block-tridiagonal solver

**Срок:** к месяцу 5

**Описание.** Добавление специализированного решателя, эксплуатирующего блочно-трёхдиагональную структуру якобиана MESH-задачи, и первое количественное сравнение с generic-подходом (dense LU). Это упрощённая версия hero-result из полного плана (без generic sparse — третьего уровня фактора).

**Состав:**
- Реализация block-tridiagonal specialized solver (алгоритм Томаса по ступеням)
- Прогон обоих солверов (dense LU из V0 и specialized) на серии размеров задачи: N = 5, 10, 20, 50 ступеней
- Замер: время на итерацию, полное время до сходимости

**Критерии выполненности:**
- [ ] Specialized solver даёт тот же результат (с точностью до допуска), что и dense LU на всех размерах
- [ ] Построен график масштабирования времени на итерацию от N для обоих солверов
- [ ] Определена и зафиксирована точка кроссовера, где specialized начинает выигрывать
- [ ] Эксперимент повторён ≥10 раз на конфигурацию, использована медиана (минимальный протокол контроля шума — полный DoE-протокол пока не обязателен)
- [ ] Результат оформлен как самостоятельный график/раздел, пригодный для защиты как главный результат

## V2 — Технические факторы кодогенерации

**Срок:** к месяцу 7

**Описание.** Введение факторов Уровня 1 (codegen/HPC) и первый настоящий факторный эксперимент (DoE), а не одиночные измерения.

**Состав:**
- Устранение динамического диспетчинга по типу ступени (специализация на этапе компиляции)
- SoA-раскладка данных вместо AoS
- Развёртка циклов по компонентам (минимум 2 уровня: без unroll / полный unroll)
- SIMD-векторизация через `#pragma omp simd` (`restrict`, выравнивание); ручные интринсики — опционально, если останется время
- Дробный факторный план на 2–3 факторах (например: dispatch × SoA × unroll), 1–2 фиксированных размера задачи
- Контроль шума: фиксированный CPU governor, отключённый Turbo Boost, 30+ повторов, bootstrap CI
- Явная документация флагов компиляции и проверка векторизации (`-fopt-info-vec` / `-Rpass`)

**Критерии выполненности:**
- [ ] Реализованы и переключаемы (build-flag или codegen-опция) минимум 3 из 4 перечисленных факторов
- [ ] Проведён факторный эксперимент (не one-factor-at-a-time) с задокументированным планом
- [ ] Для каждой конфигурации получены: медиана + CI по времени на итерацию
- [ ] Отдельно зафиксировано взаимодействие факторов (например, эффект unroll с SIMD и без него отличается)
- [ ] Подтверждено логами/отчётом компилятора, что векторизация происходит там, где предполагается, а не только за счёт auto-vectorizer `-O3`

## V3 — Аналитический якобиан (Source-transform AD)

**Срок:** к месяцу 8

**Описание.** Замена finite-difference якобиана на source-transform AD по графу выражений (Graph IR), с ручными производными для термодинамических примитивов (Antoine). Технически самая рискованная часть — до начала реализации обязателен спайк.

**Состав:**
- Спайк (месяц 1, заранее!): быстрый sympy-прототип якобиана "на коленке" для оценки сложности выражений
- Реализация Graph IR и source-transform AD в компиляторе
- Ручные производные для Antoine-примитивов
- Сравнение FD (из V0) vs AD по: числу итераций Ньютона до сходимости, времени на итерацию, полному времени

**Критерии выполненности:**
- [ ] AD-якобиан даёт тот же результат сходимости (или лучше), что и FD, на тестовых кейсах
- [ ] Замерено и задокументировано число итераций FD vs AD (гипотеза: AD даёт меньше итераций за счёт точности)
- [ ] Замерено время на итерацию FD vs AD (компромисс: AD может быть дороже за вызов, но снижает число вызовов)
- [ ] Зафиксирован факт отсутствия неконтролируемого разрастания выражений (в отличие от чисто символьного sympy-подхода) — это ключевой academic claim этого раздела
- [ ] Если спайк в месяце 1 показал чрезмерную сложность — задокументировано решение об упрощении скоупа (fallback-план)

## V4 — Внешние сравнения (подтверждение novelty claim)

**Срок:** к месяцу 10

**Описание.** Прямое эмпирическое сравнение с существующими решениями, обязательное для защиты тезиса о нише между generic codegen и domain-aware runtime. Приоритет — сравнение с CasADi (закрывает наиболее вероятный вопрос комиссии); DWSIM — вторым, по остатку времени.

**Состав:**
- Спайк (месяц 2, заранее!): проверка, что CasADi и DWSIM разворачиваются и дают воспроизводимые кейсы
- Реализация тех же тестовых кейсов (5×2, 10×3, 20×5) в CasADi codegen
- Сравнение: время на итерацию, полное время до сходимости, размер кода/бинарника
- (Опционально, если время позволяет) то же сравнение с DWSIM/ChemSep

**Критерии выполненности:**
- [ ] Минимум сравнение с CasADi выполнено на всех трёх размерах кейсов
- [ ] Сформулирован и подтверждён (или опровергнут) конкретный количественный вывод — не просто "наше быстрее", а с цифрами и объяснением источника разницы
- [ ] Если сравнение с DWSIM не выполнено — явно задокументировано как Future Work с обоснованием (нехватка времени, а не забытый пункт)
- [ ] Есть готовый ответ на вопрос комиссии "чем это лучше generic symbolic codegen"

## V5+ — Буфер (опционально, по остатку времени)

**Срок:** после месяца 10, если есть время до защиты

**Описание.** Необязательные расширения, добавляемые по одному в порядке убывания ценности/трудозатрат. Не планируются как обязательства — только как задел, если основной роадмап закрыт раньше срока.

**Кандидаты (в порядке приоритета):**
1. Precision (f32 vs f64) с протоколом обработки "not converged"
2. Разделение якобиана на структурно-постоянные и нелинейные блоки
3. Сравнение методов решения MESH (Naphtali-Sandholm vs Wang-Henke/BP vs inside-out)
4. Специализированная инициализация (Fenske-Underwood-Gilliland)
5. Parallel cyclic reduction для solve по ступеням
6. Аналитические чувствительности через факторизованный якобиан
7. Generic sparse solver как промежуточный уровень (между dense LU и block-tridiagonal)
8. WASM-кейс-стади

**Критерии выполненности:** для каждого добавленного пункта — минимум одно количественное сравнение "с фактором / без фактора" на хотя бы одном размере задачи. Пункты без замера не включаются в текст диплома как результаты — только как реализованная, но неизмеренная возможность.
