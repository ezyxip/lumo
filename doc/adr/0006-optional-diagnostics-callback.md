# ADR-0006 Условная генерация диагностики и необязательный callback

**Статус** принято, реализовано в codegen/solver и cmd/lumo

## Решение

Поддержка дополнительной диагностики включается при генерации модели
CLI по умолчанию выпускает C99 без кода диагностики, флаг `-diagnostics` включает его
В диагностической сборке данные экспортируются через необязательный callback
и указатель контекста
Если callback равен NULL, дополнительные диагностические записи не готовятся
Обязательный результат расчёта сохраняется независимо от диагностики

Вызывающий код владеет состоянием, рабочим буфером, итоговым отчётом и контекстом
В сгенерированном коде нет динамических аллокаций и операций ввода-вывода
Callback вызывается синхронно, запись доступна только до его возврата
Для сохранения истории вызывающий код копирует записи в собственную память
Время, затраченное callback, входит во внешний замер расчёта

Статус, причина остановки, число итераций и конечная норма остаются
обязательными данными результата
Историю и дополнительные метрики получает callback
Передаются начальное событие и события принятых шагов
Запись содержит номер итерации, норму невязки, норму изменения состояния,
принятый множитель шага, числа отклонённых проб и максимальную знаковую
масштабированную невязку с индексом строки
Ошибки и завершение сообщаются обязательным отчётом, отдельных событий для них нет
Если ошибка возникает до корректной начальной невязки, callback не вызывается
Время выполнения и аппаратные метрики измеряются снаружи расчётного ядра

Пользователь может выпускать две сборки одной модели
Основная сборка без диагностики используется для массовых расчётов
Диагностическая сборка позволяет исследовать отдельный проблемный расчёт
Для повторения сохраняются описание колонны, входные параметры, начальное
приближение и настройки солвера, остальные параметры сборки должны совпадать
Переключение между этими сборками выполняет вызывающий код

Сборка OFF полностью исключает код подготовки и передачи диагностических событий
Она служит базой исследования расчётного подхода без дополнительного наблюдения
Для этого не требуется доказывать нулевую стоимость NULL или измерять расходы
диагностики при каждом сравнении расчётных оптимизаций
Отсутствие кода диагностики не гарантирует минимальное время выполнения
Различия машинного кода могут влиять на скорость, поэтому утверждение о самой
быстрой сборке требует отдельных измерений
Настройка `solver.GenerationOptions.Diagnostics` управляет генерацией
`Generate` включает поддержку callback, `GenerateWithOptions` позволяет её исключить
Макрос `LUMO_SOLVER_HAS_DIAGNOSTICS` сообщает возможность наблюдения
Варианты сохраняют одинаковые типы и поля настроек, в отключённом варианте
указатели observer и context игнорируются без проверок и подготовки метрик
Полные правила API описаны в [solver](../../codegen/solver/README.md)

Сейчас CLI выдаёт исходники C99, их компиляция выполняется вручную
Выбор исполняемого файла или библиотеки остаётся будущей настройкой компилятора
Библиотека отдаёт данные через C API, вводом и выводом управляет внешняя оболочка

## Рассмотренные варианты

- Полное исключение диагностики при генерации даёт основную и контрольную сборку
- Необязательный callback позволяет пропустить сбор дополнительных метрик при NULL
- Обязательный пустой callback сохраняет стоимость подготовки записи и вызова
- Callback со сбором в память позволяет вызывающему коду управлять хранением

Для основной сборки выбрано исключение диагностики при генерации
В диагностической сборке используется необязательный callback
Его абсолютная оптимальность и нулевые накладные расходы не утверждаются

## Основания из PoC

Временный стенд собирался вне репозитория на снимках сгенерированного C99
Базой служил коммит 7d89dee с изменениями внешнего рабочего буфера солвера
Сам стенд и сырые измерения не входят в проект

Проверялись бинарные колонны с 3, 5 и 10 ступенями
Сравнивались обычное решение, остановка после одной итерации
и уже сошедшееся начальное состояние
Все варианты дали побитово одинаковое состояние, одинаковые статусы,
число итераций и итоговые нормы

Использовались Intel Core i7-12650H, закрепление потока за CPU 0,
GCC 16.2.1 и следующие флаги

```text
-O3 -march=native -fno-lto -std=c99 -DNDEBUG -Wall -Wextra -Werror
```

После прогрева порядок вариантов перемешивался
Первый обзор содержал 32 раунда, подтверждение 48 раундов для выбранных сценариев
Одна серия включала несколько запусков, время измерялось снаружи серии
Подготовка начальных состояний выполнялась до замера
Вывод, запись на диск и выделение памяти внутри замера отсутствовали
Контроль A/A повторял один и тот же код под разными метками

В PoC запись отправлялась для начального состояния и принятых шагов
Кроме готовых полей отчёта собирались alpha и максимальная масштабированная
невязка, для которой выполнялся дополнительный проход по вектору
Поэтому сравнение empty с off включает подготовку метрик,
стоимость одного косвенного вызова отдельно не измерялась

На уже сошедшемся состоянии обязательный пустой callback с подготовкой записи
добавил примерно от 8 до 18 процентов процессорного времени
Необязательный NULL в коротком сценарии с 10 ступенями показал около 3 процентов
замедления, для него нельзя утверждать отсутствие эффекта

На полноценных расчётах небольшие различия меняли знак между сериями
Стандартное отклонение времени off между подтверждающими сериями составляло
примерно от 3 до 8 процентов среднего времени в зависимости от сценария
Каждая точка уже была средним по нескольким запускам
Разброс времени отдельных серий и неопределённость парного сравнения
являются разными величинами
Контроль A/A также показал различия порядка процентов

Нулевую стоимость NULL не доказали и объяснять все различия только шумом нельзя
Измерения зависят от окружения, частоты CPU, машинного кода, состава метрик
и наличия начального события
Перенос поиска максимальной невязки в существующий проход или включение LTO
потребуют нового сравнения

## Последствия

История не требует хранения внутри библиотеки
Вызывающий код может сохранять, агрегировать или игнорировать записи
Обязательный пустой callback не используется как способ отключения диагностики
Функциональные тесты подтверждают одинаковые решения трёх режимов
Это не гарантирует побитового совпадения при других компиляторах и настройках сборки

Повторный внешний стенд на реализации из коммита `9305c00` также подтвердил
одинаковые результаты проверенных сценариев
На полноценных расчётах некоторые сборки с диагностикой оказались быстрее OFF
Причина не установлена, эти различия нельзя приписывать только проверке callback
Результаты первого PoC выше относятся к прежней реализации

Основная сборка без дополнительной диагностики остаётся базой для оценки
оптимизаций расчётного подхода
Диагностическая сборка используется для изучения сходимости отдельно от этих замеров
