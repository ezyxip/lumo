# Архитектура Lumo

Lumo на Go превращает описание идеализированной колонны в специализированные исходники C99
Полученная модель рассчитывает режим через C API, её компиляцией и запуском управляет вызывающая сторона
Эта страница описывает текущую реализацию, будущие варианты находятся в [roadmap](roadmap.md)

## Два этапа

```text
Генерация на Go

compiler_input.json
        │
        ▼
cmd/lumo → парсер v1 → валидатор v1 → генераторы → шесть пар .c/.h
                                                        │
                                           ручная компиляция C99
                                                        │
                                                        ▼
Расчёт на C                                      приложение пользователя
                                                        │
структуры питания и режима → prepare → initialguess → solver
                                                        │
                                                        ▼
                                                state и report
                                                        │
                                      извлечение продуктов и профилей
```

`compiler_input.json` фиксирует компоненты, свойства, число ступеней, места подач и давление
Эти данные определяют константы, размерность и балансы сгенерированной системы
Для их изменения требуется повторная генерация
Состав, расход и тепловое состояние питания, расход дистиллята и флегмовое число передаются при каждом расчёте

Контракт `model_input.json` описывает параметры запуска, но готового общего JSON-интерфейса на C пока нет
Приложение преобразует свои входы в C-структуры и само извлекает результат из вектора состояния
Go-парсер `ModelInput` доступен отдельно от CLI
Схема `model_output.json` задаёт формат обмена, автоматическая сериализация результата ещё не реализована

## Генерация

[`cmd/lumo`](../cmd/lumo/main.go) разбирает аргументы, читает вход, вызывает парсер, валидатор и генераторы
Затем он собирает общий набор файлов и записывает его в новый выходной каталог
Все файлы сначала создаются во временном каталоге рядом с назначением, после успешной записи каталог переименовывается
Существующий выходной путь отклоняется
CLI не вызывает C-компилятор

[`contracts/v1`](../contracts/v1/README.md) разделяет строгий разбор JSON и семантическую валидацию
Внутренним представлением служит `contractv1.CompilerInput`, отдельного промежуточного языка сейчас нет
Генераторы написаны на Go, C99 получается из встроенных в Go-бинарник шаблонов `text/template`

| Пакет | Генерируемый модуль | Назначение |
|---|---|---|
| [thermo](../codegen/thermo/README.md) | `lumo_thermo.h/.c` | Равновесие, энтальпии и flash питания |
| [mesh](../codegen/mesh/README.md) | `lumo_mesh.h/.c` | Невязка колонны и адаптер якобиана |
| [jacobian](../codegen/jacobian/README.md) | `lumo_jacobian.h/.c` | Численные производные переданной функции |
| [prepare](../codegen/prepare/README.md) | `lumo_prepare.h/.c` | Единицы, базис состава и состояние питания |
| [initialguess](../codegen/initialguess/README.md) | `lumo_initialguess.h/.c` | Начальный профиль колонны |
| [solver](../codegen/solver/README.md) | `lumo_solver.h/.c` | Масштабирование, якобиан, линейная система и цикл Ньютона |

`mesh.Generate` включает термодинамику и общий численный якобиан
Генераторы `prepare`, `initialguess` и `solver` каждый возвращают собственные файлы вместе с `Files.Mesh`
CLI вызывает их с одним описанием колонны и записывает общие зависимости один раз
Это зависимости генерации, они не задают порядок вызовов функций при расчёте

## Вызов модели

| Этап | Вход | Выход |
|---|---|---|
| `lumo_prepare_operating` | `lumo_prepare_input` | `lumo_mesh_operating` с молярными расходами, составами и энтальпиями подач |
| `lumo_initialguess_linear_T_x` | Подготовленный режим | Начальный `state` |
| `lumo_solver_solve` | Режим, `state`, настройки и рабочий буфер | Последний принятый `state`, итоговый `report` и статус |

Начальное приближение можно задать самостоятельно
У каждого этапа свой статус ошибки, следующий этап вызывается только после успешного предыдущего
Один вызов солвера выполняет весь цикл Ньютона, а не одну итерацию
Он вычисляет невязку MESH, строит якобиан, решает плотную линейную систему и подбирает длину шага
Вычисления свойств вызываются из MESH, подготовки питания и начального приближения

Порядок C-массивов соответствует порядку компонентов и подач в описании колонны
JSON-составы задаются по ID, при переходе к C API вызывающая сторона сопоставляет их с индексами
Раскладка `state` и особенности конденсатора и кипятильника описаны в [MESH](../codegen/mesh/README.md)
Пример полного вызова находится в [драйвере проверки 5×2](../references/benzene_toluene_5x2/driver.c)

## Память и наблюдение

Состоянием, рабочим буфером и отчётом владеет вызывающий код
Сгенерированные функции используют также локальные рабочие массивы, но не выделяют память в куче
Внутри модели нет файлового ввода и вывода и глобального изменяемого состояния
Один рабочий буфер можно использовать повторно для последовательных расчётов
Для параллельных вызовов нужны отдельные изменяемые буферы
Размер и правила владения описаны в [солвере](../codegen/solver/README.md)

CLI по умолчанию полностью исключает дополнительную диагностику
Флаг `-diagnostics` генерирует подготовку событий и вызовы необязательного колбека
В диагностической сборке `observer = NULL` пропускает подготовку записей
События передаются синхронно для начального состояния и принятых итераций, хранение истории принадлежит вызывающему коду
Итоговый `report` доступен в обеих сборках, время измеряется снаружи
Решение про две сборки и основания исследования находятся в [ADR-0006](adr/0006-optional-diagnostics-callback.md)

## Поддержанные случаи и границы

Текущая модель использует полный конденсатор при температуре начала кипения, равновесный кипятильник и постоянное давление
Режим задаётся молярным расходом дистиллята и молярным флегмовым числом
Термодинамика использует Antoine и идеальный закон Рауля, идеальное смешение энтальпий и постоянные теплоёмкости
Генераторы требуют явных свойств `inline`, справочник `builtin` не реализован
Массовый расход питания поддержан, массовая спецификация дистиллята не поддержана подготовкой для текущего замыкания MESH

Основной эталон бинарный, дополнительные тесты покрывают три компонента и несколько подач
Эти проверки не доказывают сходимость на произвольных колоннах и режимах
Design, реальные эффективности оборудования, боковые отборы и другие термодинамические модели остаются за границей текущей реализации
Концептуальные границы описаны в [scope](scope.md), точные уравнения в [mesh](mesh.md)

## Проверки и решения

Go-тесты проверяют контракты и генераторы, а также компилируют и запускают сгенерированный C99
Общая инфраструктура [ctest](../codegen/internal/ctest/README.md) сохраняет артефакты при сбое
[Эталон 5×2](../references/benzene_toluene_5x2/README.md) содержит независимый Python-расчёт и сквозную проверку через CLI
Она сравнивает температуры, составы, расходы, тепло и балансы в обеих сборках диагностики
Команды разработки объединены в корневом `Makefile`, `make check` выполняет общую проверку
Отчёты текущего прогона попадают в `build/validation`
Настройка CI остаётся отдельной задачей

История основных решений

- [ADR-0001](adr/0001-thermo-models-scope.md), [ADR-0002](adr/0002-feed-stage-range.md) и [ADR-0003](adr/0003-strict-units-validation.md) фиксируют исходные ограничения и поясняют их применимость к v1
- [ADR-0004](adr/0004-newton-vector-boundaries.md) определяет неизвестные на границах колонны
- [ADR-0005](adr/0005-thermo-codegen-interface.md) определяет общий интерфейс термодинамики
- [ADR-0006](adr/0006-optional-diagnostics-callback.md) определяет диагностику и владение её данными

Прежний пакет `topology` и примеры 01–03 сохранены для старого контракта
CLI и генераторы v1 их не используют, автоматической миграции между форматами нет
